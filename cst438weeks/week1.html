Understanding Software Engineering

I never quite asked myself what the difference between "programming" and "software engineering" was. Kind of mentally chalked up software engineering as a more "professional" programming (whatever that may be). Reading the book "Software Engineering at Google: Lessons Learned from Programming Over Time" definitely provided a more solid line on the difference between those 2 terms.

From my simplified understanding it's essentially:

Programming:

Writing code.

Software Engineering:

Utilizing various strategies to sustainably structure and maintain said code

I must say, I think I'm quite lucky in that I actually enjoy planning and learning about project folder structures, managing dependencies, utilizing frameworks, etc. which is what software engineering seems to be more about. Most of my peers seem to enjoy just the "coding" aspect.

With that being said, it can get overwhelming when occasionally I get flooded with dozens or even hundreds of "deprecated" warning messages in the terminal from various libraries and dependencies when compiling or starting up certain applications. I find it equally amusing when tutorials seem to acknowledge such a given state and simply say "ignore them, that's normal" (which I assume falls under the category of violating the "shifting left" strategy, ha).

Aside from the textbook materials, there were a few key concepts I learned along the way this week:

3-tier Layered Application Architecture

The controller layer extracts relevant data from a user's HTTP request and pases it to the service layer

The service layer applies application rules (including validation) and coordinates database actions through repositories

The repository layer is reponsible for performing database operations (create, read, update, delete [CRUD] without knowing why they are needed)

3-tier Layered Application Flowchart of Data Flow

The controller sends a request to the service layer. The service layer applies business logic and asks the repository for data. The repository retrieves the data from the database and returns it to the service. The service performs any additional business logic and returns the result to the controller.

So the flowchart would look something like:

controller -> service -> repository -> database -> repository -> service -> controller -> views

I would say understanding these key concepts definitely helped me in mentally understanding the structure and logic of a Springboot project
