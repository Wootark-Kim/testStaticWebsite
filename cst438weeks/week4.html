What is the most interesting thing you have learned in your reading of "Software Engineering at Google"?

I actually found the whole idea that writing code from scratch, or any new code for that matter, is a liability quite interesting. We need to write code to have something be functional, yet for a large corporation such as Google, it doesn't want any more new code. As the book already stated, "Chances are, if you are writing a utility, someone else somewhere in a codebase the size of Google’s has probably done something similar" (p. 167). So always use internal libraries instead.

Of course, it makes sense when seen from a perspective of maintaining bloat. More code means more maintenance and also much harder for a future maintainer to learn the codebase. Yet I find it quite humorous that despite such philosophy of keeping new codes to a minimum, we somehow managed to bloat every field of web or software engineering with an incredible diverse number of frameworks.

I'm also incredibly curious if the policy/process for code review at Google has changed ever since the wide adoption of AI usage. People seem to use AI more often now to check code quality when reviewing, yet... people also seem to agree that AI code itself should be reviewed by human. So... will code review eventually evolve into a strictly "human-preferred" field, or will we start creating a silly nesting doll of human reviewing an AI reviewing a human made code that was possibly made by AI code?
